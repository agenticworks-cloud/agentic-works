# Roost Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use trivialpowers:subagent-driven-development (recommended) or trivialpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One VS Code extension, `seanahn.roost`, made of Perch, chirp, jay and kestrel as parts under `parts/`, each switchable at runtime, with a generated manifest so a new part is one folder.

**Architecture:** The four repos are imported with history by `git subtree add` into `parts/<name>/`, each gaining a `part.json`. `scripts/build-manifest.js` writes the root `package.json` from the parts. Roost's `src/extension.js` reads the same `part.json` files, starts each enabled part's own `activate` with a per-part context (its own `subscriptions`, its folder as `extensionUri`), and starts or stops parts when their setting changes.

**Tech Stack:** Node, plain JavaScript (no build step), VS Code API `^1.90`, plain `assert` test scripts, `git subtree`, `@vscode/vsce` for packaging.

**Spec:** `docs/notes/101-roost.md`

The design holds every design decision; this plan holds build steps and code-level names only, and is deleted when the work merges. If a decision changes during the build, change the design in the same commit.

## Global Constraints

- Every existing id stays as it is: settings and commands `perch.*`, `chirp.*`, `jay.*`, `kestrel.*`; containers `perch`, `chirp`, `jay` (activity bar), `kestrel` (panel); webview types `perch.session`, `chirp.conversation`, `jay.ticket`, `jay.page`.
- Folder → part id → switch: `parts/perch` → `perch` → `roost.perch.enabled`; `parts/chirp` → `teams` → `roost.teams.enabled`; `parts/jay` → `jira` → `roost.jira.enabled`; `parts/kestrel` → `prs` → `roost.prs.enabled`. All default `true`; each part's views, menus, Command Palette entries and keybindings are gated on `config.roost.<id>.enabled && !roost.<id>.failed`, and Roost sets only the context key `roost.<id>.failed` (Ruling 10). Part order everywhere (settings, start-up) = folder names sorted: chirp, jay, kestrel, perch.
- Titles: Perch, Teams, Jira & Confluence, PRs.
- Extension id `seanahn.roost`, version `0.1.0`, publisher `seanahn`; Roost's identity lives in `roost.json`; the root `package.json` is generated, never hand-edited.
- `part.json` fields exactly: `id`, `title`, `entry`, `needs` (array of part ids).
- `extensionPack` carries Perch's: `seanahn.perch-audio`, `anthropic.claude-code`, `openai.chatgpt`.
- Imports from: Perch `main`, chirp `main`, jay `main`, kestrel `master`, with full history (no `--squash`).
- VS Code `^1.90`; no new npm dependency except `@vscode/vsce` as a dev dependency if packaging needs it.
- Roost's settings command: `roost.openSettings` → Settings filtered by `@ext:seanahn.roost`; Command Palette title **Roost: Settings**.
- Commits as Sean Ahn <seanahn@youriris.com> (the repo's local config); end messages with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Public repo: no company names in code, tests or commit messages.

## Review Focus

1. **A part's media and webviews under `parts/<name>/`** — images, scripts and `localResourceRoots` resolve, since the part's `extensionUri` is its folder. Test: `part context points at the part folder` (Task 3) and the real run (Task 7).
2. **Turning a part off and on again** — no duplicate command registration errors, its pollers stopped, its tabs back. Test: `off then on registers cleanly and leaves no timer` (Task 3), `tabs come back after off/on` (Task 4).
3. **A part that throws in `activate`** — one notification, the others run, toggling retries. Test: `a throwing part leaves the others running` (Task 3).
4. **A stale checked-in manifest** after a part's `package.json` changes — the tests fail. Test: `checked-in manifest equals a fresh build` (Task 2).
5. **A Perch turn running when Perch is switched off** — the user is asked; Cancel puts the setting back. Test: `switching Perch off mid-turn asks first` (Task 4).

### Task 2: The generated manifest

**Files:**
- Create: `scripts/build-manifest.js`, `package.json` (generated), `Makefile` (target `manifest`)
- Test: `test/manifest.test.js`

**Interfaces:**
- Consumes: `part.json` ×4, each `parts/<name>/package.json`, `roost.json`.
- Produces: `buildManifest(root: string): object` (pure: reads files, returns the manifest; throws `Error` naming the problem) and the CLI `node scripts/build-manifest.js [--check]` (writes `package.json`, or with `--check` exits 1 if the file differs from a fresh build). Rules:
  - start from `roost.json`; `main` = `./src/extension.js`;
  - `contributes`: union of every part's `contributes` keys (arrays concatenated, objects merged); `configuration` merged into one object titled `Roost`, with `roost.<id>.enabled` (boolean, default `true`, description `"<title>: switch this part on or off."`) listed first, in part order;
  - every entry in `views.*`, `viewsContainers.*` and `menus.*` of a part gets `when` = `roost.<id>.enabled` (or `roost.<id>.enabled && (<existing>)`);
  - `activationEvents`: union, plus `onStartupFinished`;
  - `dependencies`: union of the parts' `dependencies` (a version conflict throws); `extensionPack`: union;
  - throws on: a duplicate id among commands, configuration properties, views, view containers, or webview types in `activationEvents`; a part folder without `part.json`; a `needs` naming no part; two parts with the same `id`.
- `Makefile`: `manifest: ; node scripts/build-manifest.js`.

- [ ] **Step 1: Write the failing tests** in `test/manifest.test.js` against temp fixture trees (two small fake parts) and the real tree:
  - `union keeps every id` — fixture commands `a.x`, `b.y` both present unchanged.
  - `when added` — a fixture view with `when: "foo"` becomes `roost.b.enabled && (foo)`; one without becomes `roost.b.enabled`.
  - `switch settings first, default true`.
  - `duplicate command id throws` (message names the id and both parts); `missing part.json throws`; `unknown needs throws`; `dependency version conflict throws`.
  - `real tree builds` — `buildManifest('.')` succeeds, has `name: roost`, the containers `perch`, `chirp`, `jay`, `kestrel`, Perch's two SDK dependencies and its `extensionPack`.
  - `checked-in manifest equals a fresh build` — `node scripts/build-manifest.js --check` exits 0.
- [ ] **Step 2: Run** `node test/manifest.test.js` — Expected: fails.
- [ ] **Step 3: Implement** `scripts/build-manifest.js`; run `make manifest` to write `package.json`.

### Task 3: The loader — start, stop, isolate

**Files:**
- Create: `src/extension.js`, `src/parts.js`, `test/vscodeStub.js`
- Test: `test/loader.test.js`

**Interfaces:**
- Consumes: `part.json` files; each part's `entry` exporting `activate(context, deps?)` and optional `deactivate()`.
- Produces:
  - `src/parts.js`: `readParts(root: string): Part[]` (`{ id, title, dir, entry, needs }`, folder order alphabetical); `partContext(base: ExtensionContext, part: Part): ExtensionContext` — same `globalState`, `workspaceState`, `secrets`, `storageUri`, `globalStorageUri`, `logUri` as `base`; `extensionUri`/`extensionPath`/`asAbsolutePath` resolved to `part.dir`; its own `subscriptions: []`.
  - `src/extension.js`: `activate(context)`, `deactivate()`; a `Roost` object with `start(id)`, `stop(id)`, `state(id): 'on'|'off'|'failed'`. `start` sets the context key true only after the part's `activate` returned; a throw → state `failed`, key false, one `showErrorMessage("Roost: <title> could not start.", "Show Log")`, the error in the `Roost` output channel; `stop` disposes the part's subscriptions (each in its own try/catch), calls `deactivate`, sets the key false; `onDidChangeConfiguration` for `roost.<id>.enabled` calls `start`/`stop`; turning a `failed` part off then on retries.

- [ ] **Step 1: Write the failing tests** in `test/loader.test.js` (Node `Module._load` hook serving `test/vscodeStub.js` for `vscode`, fake parts in temp dirs):

  - `part context points at the part folder` — the context a part receives has `extensionUri.fsPath === part.dir` and `asAbsolutePath('media/x.svg') === path.join(part.dir, 'media/x.svg')`, and shares `globalState` with the base.

  - `off then on registers cleanly and leaves no timer` — a fake part registering a command and a `setInterval` in its subscriptions: off disposes both (`clearInterval` seen, command unregistered); on again registers without the stub's duplicate-command error.
  - `stop survives a throwing dispose` — one disposable throws → the part is still `off`, its other disposables still disposed.

### Task 4: Tabs of a part that is off; asking before stopping Perch

**Files:**
- Modify: `src/extension.js`, `parts/perch/src/extension.js` (exports), the parts' `deactivate`/dispose paths only where a test shows saved tabs being lost
- Test: `test/loader.test.js`, `parts/perch/test/host.test.js`

**Interfaces:**
- Produces:
  - **Optional part export** `confirmStop(): Promise<boolean>` — Roost calls it before `stop`; `false` cancels the stop and Roost writes `roost.<id>.enabled = true` back at the scope it was changed in. Perch implements it: if any Perch session is busy, `showWarningMessage("Stop the running turn and close Perch's tabs?", { modal: true }, "Stop")` → true only on "Stop"; else true.
  - **Serializers for parts that are off:** for every `onWebviewPanel:<type>` in a part's `package.json` `activationEvents`, while that part is off, Roost registers a serializer whose `deserializeWebviewPanel(panel)` disposes the panel; it disposes that registration before starting the part (so the part's own registration does not collide).
  - **Saved tabs survive off/on:** after a part is stopped, the tabs it had open come back when it starts again (each part already restores its tabs from its own saved state at `activate`; where stopping clears that state — e.g. Perch's `dispose` with `closing = true` — change it so a stop keeps the saved list, as a window close does).
